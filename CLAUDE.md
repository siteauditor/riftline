# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Riftline is a League of Legends analytics site (op.gg style): FastAPI + SQLAlchemy 2.0 async + SQLite behind a React 19 + Vite + Tailwind v4 frontend, live at https://www.rhasta.space. `README.md` explains most design decisions and the Riot API traps; read it before changing anything that talks to Riot. `docs/deploy.md` is the production runbook. The roadmap is `internal-docs/feature-gap-analysis.md` (work is organised in its lettered feature groups). `internal-docs/` is gitignored: it exists on the owner's workstation and not in a clone, and anything written there stays private.

## Commands

Backend commands run from `backend/` with the venv's interpreter (`.venv/Scripts/python.exe` on Windows, `.venv/bin/python` elsewhere):

```bash
python -m uvicorn app.main:app --reload          # :8000, /docs, /api/health
python -m pytest -q                              # whole suite, no network needed
python -m pytest tests/test_scores.py -q         # one file
python -m pytest "tests/test_integration.py::test_mastery_reads_the_shard_the_account_is_on" -q
python -m pytest -q -k shard                     # by name substring
python -m ruff check app scripts tests
python -m scripts.migrate                        # additive schema migration, idempotent
python -m scripts.ingest status                  # also: crawl, timelines, lobbyranks, ladders, aggregate, score, reextract, winmodel, reviews, audit, groups, draftpriors
```

Frontend commands run from `frontend/` (pnpm is pinned by `packageManager`):

```bash
pnpm dev        # :5173, proxies /api to 127.0.0.1:8000
pnpm build      # tsc -b, then the browser bundle and the server bundle: this is the type check
pnpm lint       # oxlint
pnpm test       # vitest: the lib and component tests, jsdom, no network
pnpm api:types  # src/lib/api.gen.d.ts from openapi.json (written by `python -m scripts.openapi ../frontend/openapi.json` in backend/)
pnpm exec playwright test   # e2e/smoke.spec.ts against a served build (E2E_BASE_URL, default the page server on :6123); CI runs it on the prerendered pages
pnpm prerender --api http://127.0.0.1:8000 --out /tmp/pages --build-id local   # every page as HTML, from a running API
node prerender/serve.mjs --pages /tmp/pages/local                             # serve them in nginx's try_files order
```

CI (`.github/workflows/ci.yml`) runs the same suite, ruff, build and lint inside the Docker images, plus an em dash check.

## Architecture

### Backend

`app/riot` (HTTP client, rate limiter, host routing) -> `app/services` (all logic) -> `app/api` (routes, and `schemas.py`, which holds the response models and the ORM-to-response mappers). `scripts/ingest.py` drives the services as a CLI.

**Riot host routing is where most bugs have come from.** `app/riot/routing.py` maps each platform to its regional host (match-v5) and its account-v1 region (SEA collapses to `asia`). A Riot ID resolves across a whole region, but summoner-v4, league-v4, champion-mastery-v4 and spectator-v5 answer only for the shard the account lives on, and on the wrong shard the last three return **200 with nothing** rather than an error. OCE Riot IDs are the usual case: they resolve through `sea` while the account lives on `sg2`. `Player.platform` is the home shard, as account-v1's active-region lookup names it (`RiotClient.active_region`, asked with the account on every cold lookup), and it changes only through `homes.move_home` or the `homes` repair stage. **Only the home's summoner record, ranks and mastery are stored**: the storing methods (`ensure_summoner`, `ranks`, `masteries`) take no platform, and a request that names another shard goes through `PlayerService.view()`, which answers `home`, `second` (the account holds a rank or stored games there: read with `league_on`, `summoner_on`, `masteries_on`, kept in memory only) or `absent` (answered with the home's data and `plays_on`, and the page moves to the home's address). `RankCache.get_many` stores a lobby's ranks only for players whose home is the lobby's shard. A view of NA for a EUW Challenger with a level 30 NA record deleted their rank on 2026-09-24 under the old rule, which rewrote every cache for whichever shard a URL named. Every per-shard cache on `Player` still records the shard it came from (`summoner_platform`, `league_platform`, `mastery_platform`); a new per-shard cache needs the same stamp and the same home-only rule. One Riot question is asked once however many requests want it: `app/services/flight.py` (`flights`, and `TtlCache` for answers kept in memory). `ph2` and `th2` are aliases to `sg2`: Riot merged those shards and their hosts no longer resolve, so they must not come back into `PLATFORMS`; `platform_ids_for` says which stored match prefixes count as a shard (SG2 counts PH2 and TH2).

**Storage first.** `matches.raw` holds the full match-v5 payload and `match_timelines.raw_gz` the gzipped timeline, so most new features can be computed from disk without spending the rate limit (a development key allows 100 requests per two minutes). The Riftline performance score (`app/services/scores.py`) is computed entirely from stored data: percentile breakpoints per (queue, role, metric) in `role_metric_stats`, combined with the published per-role `WEIGHTS`. Bumping `WEIGHTS_VERSION` marks existing scores stale.

**Ingestion order matters:** `homes` (storage only, first in the nightly) -> `crawl` (finds matches) -> `timelines` -> `lobbyranks` -> `aggregate` -> `score`. `aggregate` and `score` make no Riot calls. `score --rebuild-distributions` re-measures the percentiles and rescores every lobby; `score --rescore` recomputes scores left stale by a weights change.

**Schema changes have no Alembic.** `init_db` (`create_all`) creates new tables but never alters existing ones, so a new column on an existing table must also be added to `ADDITIVE` in `scripts/migrate.py`. Every deploy runs the migration. A new column on a table the API reads takes two deploys: `deploy.sh` starts the new API and runs its health check before it migrates, so the first deploy only adds the column to `ADDITIVE` and the model declares it in the next. A column filled from `matches.raw` must also join `_unlifted()` in `app/services/scores.py`, the cursor of the backfill the score stage runs, or rows stored before the column existed are never filled.

**Database path.** A relative `DATABASE_URL` is anchored to the repository root (`PROJECT_ROOT` in `app/db/base.py`), so the local corpus is `data/lol.db` at the repo root, not under `backend/`. The Docker image mirrors that layout (`/srv/riftline/backend` beside a `/srv/riftline/data` volume) for the same reason.

**Numbers are withheld rather than guessed.** Thin samples are shown with their sample size or not shown at all: tier lists rank by Wilson lower bound, scores are withheld below `MIN_GAMES_FOR_SCORE` games per role, and responses carry `basis` / sample fields that say what a figure was computed from. New statistics should follow the same pattern. Floors that several pages share live beside `TIER_MIN_GAMES` in `app/services/aggregate.py` (`MIN_LANE_TIMELINES`, `MIN_LANING_TIMELINES`), and the API applies them: a figure under its floor is null in the response, with the sample beside it, rather than hidden by one page and shown by another. Tier letters are banded among the rows with `TIER_MIN_GAMES` or more whatever floor a page displays, so a letter reads the same everywhere.

**The draft, the live page and the champion page read records one way.** `app/services/evidence.py` turns a matchup or synergy record into a lift and a call (favoured, unfavoured or level) from one posterior, each patch read against the champion's own rate on that patch, with prior strengths set from a measurement (`LANE_STRENGTH` and the rest). Only lane records move the draft's ranking. Enemy-team and ally records, and the team damage mix (`app/services/damage.py`), are shown with their samples and not scored, because on this corpus they have not been measured to repeat or to matter. `evidence.parts_by_patch` groups a record's rows per patch for it, so a new reader pools patches the same way. `python -m scripts.ingest draftpriors` re-measures all of it, and the spread of champion win rates and of players' scores behind the tier list's separation line and the best-players board; change a strength, or score a new kind of evidence, only when it says so.

### Tests

`tests/conftest.py` points `DATABASE_URL` at a temporary SQLite file before any app module is imported, zeroes every cache TTL and unthrottles the limiter. Riot is mocked with `respx` at the HTTP transport layer, so everything above it is production code.

The whole suite shares **one database**. A test that inserts rows needs ids no other test uses. The single-letter puuids (`"C" * 78`) are mostly taken, so name them instead (`"my-test".ljust(78, "0")`); a collision surfaces as a UNIQUE constraint failure far from the cause. Because the TTLs are zeroed, a request-level test cannot tell a scoped cache from a cold one, so cache-scoping tests drive the service directly (see `test_the_summoner_cache_is_scoped_to_one_shard`).

### Frontend

`src/lib/api.ts` is the typed client. Its response types are aliases of `src/lib/api.gen.d.ts`, generated from the API's OpenAPI document: after any change to a response model, run `python -m scripts.openapi ../frontend/openapi.json` in `backend/` and `pnpm api:types` in `frontend/`, and commit both files; CI regenerates them and fails on a difference. A response field must therefore have a real type on the backend (a model, or a `Literal` for a fixed vocabulary), never `dict` or `Any`, or the page compiles against `unknown`. The client fetches relative `/api/...` paths, which the Vite dev server and the production nginx (`frontend/nginx.conf`) both proxy, so there is no CORS. Routes live in `src/routes.tsx`, shared by the browser entry (`src/main.tsx`) and the prerender entry (`src/entry-server.tsx`).

**Every page is prerendered.** `prerender/run.mjs` renders each path in `GET /api/meta/pages` to a file nginx serves; the shell is `noindex`, so a URL is indexable exactly when it has a prerendered file (`app/services/seo.py` decides which, on the site's sample floors). A route that is prerendered declares the queries it reads in its `handle.prefetch` using the definitions in `src/lib/queries.ts`, and its component must read them through the same definitions, or the page hydrates with an empty cache and fetches everything again. Every route renders `<Head>` (`src/lib/seo.ts`) for its title, description and canonical; the prerenderer writes those tags and the client updates them in place. Anything that reads `Date.now()`, the timezone or the browser locale in render goes through `src/lib/clock.ts` (`useNow`, `useLocalOffsetHours`, `components/TimeAgo.tsx`) or a pinned locale (`toLocaleString('en-US')`, `shortDate`), or the hydrated text mismatches the HTML. Champions and items are addressed by slug (`/champions/aatrox`); ids still resolve and redirect. A champion's role is a path word (`/champions/pantheon/support`, words in `ROLE_WORDS`, which `app/services/seo.py` and `src/lib/searchParams.ts` both hold): the bare path is the main role, a role with 20 games is its own indexed page, and the main role's path points its canonical at the bare path. Build every champion link with `championPath(champion, position?, slice?)`, never by hand and never with `?position=`, which the page reads only to move it into the path. Profiles are prerendered from storage only (`?source=stored` on the summoner routes, `queries.*Stored`), for players with ten scored games and a known Riot ID; the page shows the stored answers as placeholder data and its live queries replace them. A player has one address: build every summoner link with `summonerPath(platform, name, tag, tab?)` (`src/lib/profileAddress.ts`), never by hand, and `profileRedirect` moves a profile opened on a shard the account holds nothing on to its home, and an alias or another spelling to the canonical address, after hydration and on the live answer only.

**Profiles are also rendered on request.** `prerender/live.mjs` (the `render` service) renders a profile that has a file with `live: true` in its prefetch context, so the header's profile is asked live (`queries.profile`) and the title a crawler or link preview reads carries the current rank; a live query that fails or passes the three-second budget is dropped, and the page renders exactly as its file. nginx serves the file whenever the renderer cannot answer. A new live query in a prefetch must follow the same rule: optional, bounded, and removed from the cache when it fails.

**URL state read in render goes through `useHydratedSearchParams`** (`src/lib/searchParams.ts`), which answers with empty params until hydration has finished. nginx serves the bare path's HTML whatever the query string, so a component that read the real params while hydrating did not match it: React error #418 on every link with a query string, on every page, until 2026-09-24.

**The controls are Radix primitives** under `src/components/ui/` (they began as shadcn/ui's and are restyled in the site's language; edit them freely, they are ours). Use `SelectField` for every select (Radix refuses an empty item value, so an "any" choice is a word like `all` mapped back to null; a sample floor is the presets of `minGamesOptions`, never a number box), `Hint` (a Tooltip; its child must be focusable, so wrap a disabled button in a `span tabIndex={0}`) rather than a `title` attribute, `Button` or `buttonVariants` rather than a hand-styled button, `ChipGroup` and `Chip` for a row of filter pills (`ChipLink` when each choice is a page, as a champion's roles are), `DropdownMenu` for a menu of places (the header's pages below lg are one, `SiteMenu` in `App.tsx`, fed by the same `NAV` list as the row), `Tabs` for in-page tabs and `NavTabs` for tabs that are routes (both slide one gold bar between items through `src/lib/useSlidingBar.ts`; a trigger's own edge is hidden while the bar is present, `OWN_EDGE_CLASS`). Confirm a completed action with a toast (`toast()` from sonner; the `Toaster` in `App.tsx` carries the site's colours) and a figure that may count up with `CountUp` (it counts only on a page the app navigated to, since a prerendered figure must hydrate at its value). `@/` is `src/`. The site is dark only: `<html class="dark">` makes the components' `dark:` variants the only ones. A control that shows a value must render it on the server too (see `SelectField`, which hands the label to `SelectValue`); Radix fills some things in after mount. Anything that drops over the page (a suggestion list, a menu) is portalled through a Radix `Popover`, `Select` or `DropdownMenu`, never positioned in place: the art headers hide their overflow and clip it.

**The look is set in `src/index.css`.** Colours and radii are `@theme` tokens (a deep navy in three layers, teal for the interface, gold for what is earned, violet only inside a gradient or a glow, and the game's own orange, blue and white for physical, magic and true damage); `.frame` is the panel, `.glass` the header, `.glow` the one lit surface, `.text-gradient` the hero headline, `.skeleton` the shimmering placeholder. Loading states are skeletons that trace the real layout (`StateViews.tsx`: `TableSkeleton`, `GridSkeleton`, `ProfileSkeleton`, `MatchListSkeleton`), not spinners; `Spinner` is for a small inline "still fetching". Images below the fold carry `loading="lazy" decoding="async"`, and every image inserted after first paint fades in from a `@starting-style` rule. The fonts (Barlow, Barlow Condensed) are self-hosted through `@fontsource` imports at the top of `index.css`, so no request leaves the origin for them; `main.tsx` reloads once when a hashed chunk fails to load after a deploy, and the prerender job keeps each kept build's hashed files in the pages volume (`_shared/assets`, which nginx falls back to), so a page from the edge cache still finds its own. `main.tsx` also marks the prerendered answers that come from the nightly rollups (`ROLLUP_QUERIES`) as fetched at load, so a page does not ask again for what it was rendered with; a new rollup-backed query belongs in that list.

**Motion comes from the platform.** Page changes are view transitions: give a `Link` or `NavLink` that moves between pages the `viewTransition` prop and the document cross-fades, with the header held still by its `view-transition-name`. Anything that opens or closes animates with CSS (a grid row from `0fr` to `1fr` for an unknown height, `animate-in fade-in-0` from tw-animate-css for a section that replaces another). There is no animation library, and `prefers-reduced-motion` turns all of it off in one rule at the end of `index.css`.

**Pages are code-split.** Every page route in `src/routes.tsx` is `lazy`; `main.tsx` imports the modules the first location matches before it hydrates, so a prerendered page never hydrates against a router that has nothing to show yet. Keep a route's `handle.prefetch` on the route object, not in the lazy module, and keep anything a route needs before it renders (sample floors, query definitions) in `src/lib/queries.ts` rather than exported from the page. The React Compiler is on (`vite.config.ts`): write plain components and hooks, no manual `useMemo` or `useCallback`, and keep to the rules of hooks or the compiler silently skips the component. `useDebounced` takes a primitive: debounce a canonical string such as the draft's `requestKey(board)`, never an object, which is a new value on every render and re-rendered the draft four times a second.

**The draft page** is `src/routes/Draft.tsx` over the parts in `src/components/draft/` and its `useDraftBoard` hook. The board lives in the URL, parsed and normalised by `src/lib/draftBoard.ts`, and every change is one pure transform of the board followed by one URL write: two writes in one action lost the first, which left a removed lane opponent on the board.

Tailwind v4 is configured CSS-first: theme tokens are in `@theme` in `src/index.css`, and there is no `tailwind.config`. Custom classes must go inside `@layer components` (or `base`), because unlayered CSS beats every utility and silently overrides classes like `px-3` or `font-700` on the same element. Native `<select>` popups are styled by `.control` / `.control-bare` in the same file, which set both the option background and its colour explicitly; relying on inheritance or `color-scheme` alone has produced unreadable dropdowns twice.

## Deployment

Production is a shared VPS that also serves five other sites. Read `docs/deploy.md` before changing `deploy/`, the workflow, or anything on the server.

- A push to `main` runs CI on GitHub-hosted runners, then the deploy job connects over SSH with a forced-command key. The server runs `/usr/local/bin/riftline-deploy`, which accepts only a commit sha that is on `main`, then runs `deploy/deploy.sh`.
- The repository is public. Never add a self-hosted runner (a pull request could run code on the server through it), and never add repository-level secrets: the deploy secrets live on the `production` environment, which fork pull requests cannot reach.
- `deploy/riftline-deploy`, the systemd units and `deploy/cloudflare-only-web` are installed outside the deploy directory, so a push does not update them. Reinstall them as `docs/deploy.md` describes.
- `main` has a ruleset (changes go through a PR that passes "Tests and build", and no force-pushes). The owner can bypass it.

## Repository rules

- Never write the em dash character, anywhere: code, comments, docs, commit messages. CI fails if one appears under `backend/`, `frontend/src`, `docs/`, `deploy/` or `.github/`, or in the `Makefile` or `docker-compose.yml`; files at the repository root (this one, `README.md`) and commit messages are not scanned, so check those yourself.
- Never print the Riot API key. `backend/.env` and `data/` are gitignored and must stay untracked.
- Commits are authored as `Rhasta <244224210+Rhasta0323@users.noreply.github.com>`. That is set in this clone's `.git/config`; a fresh clone needs it set again, because the history was rewritten to remove a personal address.
- Comments in this codebase explain why, usually naming the measurement or the failure that motivated the code. Match that in new code.
